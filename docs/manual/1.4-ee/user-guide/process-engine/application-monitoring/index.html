    Application Monitoring

    Enterprise Edition 1.4.3-ee and later

    The co-released modules and container support below are part of Enterprise 1.4.3-ee and later. Earlier releases use the separate monitor extension and support Spring Boot / Run only. Use the same Enterprise release for the engine, the External Task Client and the monitoring modules; the new coordinates are not a drop-in dependency for older clients.

    Application monitoring exposes Micrometer meters for the engine and external-task workers. Its source now lives under monitoring/ in the engine repository and is released in the same reactor. There is no monitor-to-released-engine-to-monitor release cycle. The existing database-reported engine Metrics remain a separate mechanism.

    Modules and migration

    All six production artifacts use group org.eximeebpms.bpm.monitor and the engine release version:

    ArtifactPurpose
    eximeebpms-monitor-commonShared catalog, Micrometer helpers and registry factory SPI; no engine or Spring dependency
    eximeebpms-monitor-engineEngine measurements and the container lifecycle plugin; no Spring dependency
    eximeebpms-monitor-clientReusable worker measurements; depends on the Java client, not the engine
    eximeebpms-monitor-spring-bootAuto-configuration for engine/client meters and Actuator authorization
    eximeebpms-monitor-prometheusPrometheus registry factory and text exposition for containers / plain Java
    eximeebpms-monitor-webappServlet WAR served at /metrics by Tomcat and WildFly

    Remove the old org.eximeebpms.bpm.extension.monitor:eximeebpms-enterprise-bpm-spring-boot-monitor dependency (or its Community predecessor eximeebpms-bpm-spring-boot-monitor). Do not keep old and new implementations on the same classpath: their Java packages intentionally remain compatible and would overlap. The migration also brings ad-hoc subprocess turn and model usage meters (see Ad-hoc subprocesses) and fixes explicit @EnableMonitoring registration.

    For applications using the engine REST starter, the new engine and Boot monitoring modules are included by the starter. Other embedded-engine Boot applications add both modules explicitly:

    <dependency>
  <groupId>org.eximeebpms.bpm.monitor</groupId>
  <artifactId>eximeebpms-monitor-engine</artifactId>
  <version>${eximeebpms.version}</version>
</dependency>
<dependency>
  <groupId>org.eximeebpms.bpm.monitor</groupId>
  <artifactId>eximeebpms-monitor-spring-boot</artifactId>
  <version>${eximeebpms.version}</version>
</dependency>

    Set eximeebpms.version to the same published Enterprise version as the engine. Add the chosen exporter separately. For Prometheus, add org.eximeebpms.bpm.monitor:eximeebpms-monitor-prometheus at the same engine version; it includes the registry and the monitoring-specific naming convention. Auto-configuration needs no application-package scan. Existing applications using @EnableMonitoring remain supported; do not also install EngineMonitoringPlugin in a Boot engine, because it would observe the same events twice.

    Worker applications use Worker Monitoring. Adding worker monitoring does not pull the engine or its database runtime into the worker.

    HTTP export and authentication

    Measurement and HTTP exposure are separate. Run keeps /actuator/prometheus; enable its exposure through the existing management.endpoints.web.exposure.include configuration. The endpoint requires an authenticated principal with role metricsreader, even when other Actuator endpoints are public. Exposing an endpoint does not grant that role.

    Run’s shipped configuration exposes only the Actuator endpoints health and prometheus. If you expose more, Run lets only engine administrators read them, metricsreader alone is not enough; health stays open.

    Run always authenticates the Prometheus path, and every other Actuator endpoint except health, against the engine’s identity service, whether or not eximeebpms.bpm.run.auth.enabled protects the REST API, and with any combination of the --webapps and --rest components. It accepts HTTP Basic credentials and, on the main server, an existing login to Cockpit, Admin or Tasklist in the same browser session; a separate management server keeps its own sessions and accepts HTTP Basic only. Engine administrators (the engine’s adminUsers and adminGroups, by default group eximeebpms-admin) may read metrics; any other user must belong to group metricsreader. The stock demo account is an administrator, so after logging in to Cockpit you can open /actuator/prometheus in the same browser. No additional credential store is created. Run registers this check on both the main and a separate management server. Endpoint path overrides (management.endpoints.web.base-path, management.endpoints.web.path-mapping.prometheus, management.endpoints.web.path-mapping.health) are respected.

    With the --oauth2 component, a user who logged in through the OAuth2 provider is checked the same way. The OAuth2 identity provider takes that user’s groups from the token, so map the provider’s groups into it with eximeebpms.bpm.oauth2.identity-provider.group-name-attribute: a token group metricsreader, or an administrator group such as eximeebpms-admin, grants access. A scraper keeps using HTTP Basic with an account of the engine’s database identity provider.

    A state-changing Actuator request in Run (any method other than GET, HEAD and OPTIONS, for example POST /actuator/loggers/ROOT when loggers is exposed) that is authenticated through a Cockpit, Admin or Tasklist login or an OAuth2 login must send the session’s CSRF token in the X-XSRF-TOKEN header; a missing or invalid token returns 403. With a web application login, its existing CSRF token is accepted. Run also returns a token of its own in the X-XSRF-TOKEN response header, marked Cache-Control: no-store, on every authorized GET, HEAD or OPTIONS to a protected Actuator endpoint made through a login session, so a client without the web applications’ token, such as one using OAuth2 without --webapps, can:

    1. With the login session, send GET to an exposed Actuator endpoint other than health that the user may read, for example /actuator/loggers or, for a metricsreader user, /actuator/prometheus.
    2. Read X-XSRF-TOKEN from the response headers. Do not write the token to logs or shared caches.
    3. Keep the same login session and send that token in the X-XSRF-TOKEN request header on the modifying request.

    Run’s token is separate from the web applications’ token and does not change their cookies; obtain a new one after the session expires. health issues no token. A browser resends HTTP Basic credentials by itself once they are entered, so a state-changing HTTP Basic request that carries an Origin or Sec-Fetch-Site header, as browsers send, must also send a non-empty X-XSRF-TOKEN header; any value is accepted, because a page on another site cannot add that header to a request to Actuator unless management.endpoints.web.cors allows that site. Such requests get no token and create no session. Scripts and scrapers that send neither header are not affected. A request that carries a login identity is checked as a session request even if it also sends Basic credentials.

    The administrator exception exists only in Run, which checks identities itself. Tomcat, WildFly and your own Spring Boot application authorize the metrics endpoint by role metricsreader alone: an engine administrator without that role is denied.

    In your own Spring Boot application the endpoint uses the principal and roles of the application’s existing security mechanism. With Spring Security, the role is the granted authority ROLE_metricsreader, for example User.withUsername("scraper").password(...).roles("metricsreader"). When the role comes from a JWT or OAuth2 claim, map it with the ROLE_ prefix (for example JwtGrantedAuthoritiesConverter.setAuthorityPrefix("ROLE_")); an authority named just metricsreader is not the role and results in 403. An application using a separate management server must configure its security mechanism on that server too.

    Container distributions include metrics.war. Set httpEnabled=true on the engine’s monitoring plugin to opt in; it is false by default. The WAR exports only engines whose plugin enables HTTP export; when no engine does, /metrics answers 404. It uses the container’s authenticated principal and metricsreader role. The stock descriptor uses BASIC against the existing Tomcat Realm / WildFly application security domain; no users are packaged in the WAR. Deployments with SSO adapt the standard WAR login configuration and role mapping to their existing mechanism. Do not create a second metrics-specific user database. Access is operational and server-wide: the role can read every engine selected for export by this WAR.

    Tomcat’s WAR context is /metrics (including an exact request without the trailing slash). WildFly’s jboss-web.xml declares the same context root. Route this path through the installation’s existing transport and access controls.

    Authenticated scrape examples

    For stock Run, enable monitoring (eximeebpms.monitoring.enabled=true) and expose the endpoint. The shipped default.yml disables monitoring; production.yml enables it:

    eximeebpms:
  monitoring:
    enabled: true
    snapshot:
      updateRate: 10000
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
  endpoint:
    prometheus:
      access: read-only
  prometheus:
    metrics:
      export:
        enabled: true

    Enable both the endpoint and the Prometheus registry when overriding a Run configuration that disables them; HTTP exposure alone does not enable a disabled endpoint. Set the endpoint with management.endpoint.prometheus.access, as the shipped files do. Do not also set the deprecated management.endpoint.prometheus.enabled anywhere in the configuration, including in a configuration carried over from an earlier release: Spring Boot refuses to start when both keys are set for the same endpoint. The group id metricsreader matches the database identity provider’s default group id pattern, so it can be created in Admin without changing group-resource-whitelist-pattern.

    For a scraper, use a dedicated account that is not an engine administrator, with HTTP Basic rather than a copied session cookie, which would keep that web application session alive. Through that identity provider’s existing administration, assign the existing scraper account to group metricsreader. With the engine’s database identity provider this is the existing Admin application’s group/membership management; with LDAP/another provider, assign the corresponding group there. The monitor does not create the account or group automatically.

    # curl prompts for the account's existing password.
curl --fail --user "$SCRAPER_USER" http://localhost:8080/actuator/prometheus

    For the stock Tomcat UserDatabaseRealm, add <role rolename="metricsreader"/> in the existing conf/tomcat-users.xml and append metricsreader to the existing scraper user’s roles attribute (for example roles="scraper,metricsreader"). Keep its existing managed account and other roles. A fresh distribution defines no users there; add one outside the commented examples, for example <user username="scraper" password="..." roles="metricsreader"/>. If the installation already uses a different Realm, map the role in that Realm instead. Enable the plugin’s httpEnabled and scrape:

    curl --fail --user "$SCRAPER_USER" http://localhost:8080/metrics

    For the stock WildFly ApplicationRealm, append the role in the existing standalone/configuration/application-roles.properties entry, for example:

    existing-scraper=existing-role,metricsreader

    On a fresh distribution, create the application user with the role instead:

    bin/add-user.sh -a -u scraper -g metricsreader

    Without -p, the script asks for the password interactively; scripted installations pass it with -p.

    The supplied WAR uses the existing other application security domain, which maps to the distribution’s ApplicationDomain/realm. Preserve any existing groups and credentials, enable httpEnabled, and scrape the same /metrics path. For an installation with another configured security domain, adapt jboss-web.xml and its existing role decoder/mapping to that domain.

    These stock examples use the distribution’s existing BASIC mechanism. An installation already configured for another mechanism replaces the WAR’s standard login configuration through its normal deployment configuration. For example, an existing container CLIENT-CERT installation uses <login-config><auth-method>CLIENT-CERT</auth-method></login-config> while preserving the servlet mappings and metricsreader constraint, and maps certificate principals to that role in its existing realm. SSO integrations likewise supply their existing principal/role mapping; BASIC is not a second credential store layered over them. Apply the installation’s usual transport URL and security policy rather than copying localhost/plain-HTTP examples as production routing.

    Troubleshooting the metrics endpoint

    StatusLikely cause
    401No login or wrong credentials. A browser login counts only on Run’s main server, not on a separate management port. After repeated wrong passwords the engine temporarily throttles login attempts for that account, so correct credentials also fail for a short time.
    403In Run, for a modifying request through a login session: the X-XSRF-TOKEN header is missing or does not match the session’s token (the response then carries X-XSRF-TOKEN: Required). Otherwise, the user is authenticated but lacks the role. In Run: neither an engine administrator nor in group metricsreader (with --oauth2: neither group is in the token). In Tomcat/WildFly: the realm user lacks role metricsreader; engine administration does not count. In Spring Boot: the authority is not ROLE_metricsreader.
    404Run or Spring Boot: the endpoint is not exposed or not enabled (management.endpoints.web.exposure.include, management.endpoint.prometheus.access, or the deprecated .enabled in an application’s own configuration, and management.prometheus.metrics.export.enabled); Run answers 401 instead until the caller logs in. Tomcat/WildFly: no engine has httpEnabled=true; only a user with role metricsreader sees the 404, others get 401 or 403.

    Container configuration and lifecycle

    Tomcat configures the plugin under the process engine in conf/bpm-platform.xml; WildFly configures it under the engine’s subsystem <plugins> element in standalone.xml or standalone-full.xml:

    <plugin>
  <class>org.eximeebpms.bpm.extension.monitor.EngineMonitoringPlugin</class>
  <properties>
    <property name="httpEnabled">true</property>
    <property name="updateRate">10000</property>
    <property name="snapshotEnabled">true</property>
  </properties>
</plugin>
    Plugin propertyDefaultMeaning
    enabledtrueEnable measurement for this engine
    httpEnabledfalseAllow this engine’s registry to be exported by the WAR
    snapshotEnabledtruePoll database snapshots
    historyEnabledtrueObserve history events for counters; history level still applies
    updateRate10000Positive delay in milliseconds between completed snapshot refreshes
    engineTagtrueAdd the engine name to this plugin’s meters
    shutdownTimeout5000Maximum milliseconds to wait for an in-flight snapshot at shutdown
    schedulerJndiNameunsetOptional managed ScheduledExecutorService lookup

    The supplied WildFly configuration sets schedulerJndiName to java:jboss/ee/concurrency/scheduler/default. Preserve that setting to use the managed scheduler. Tomcat uses a plugin-owned daemon scheduler. Each engine needs its own plugin instance. Programmatic integrations can supply a registry and/or scheduler before engine initialization; these remain caller-owned. The plugin scopes its meters locally and removes them at close, without closing the caller’s registry, scheduler or unrelated meters. Reserve each engine’s monitoring names/tags for that plugin. The WAR requires a plugin-owned registry: httpEnabled=true with a caller-supplied registry fails startup, because that registry could also contain host meters or an engine that did not opt into export. Expose a caller registry through the host application’s own protected endpoint instead.

    At close the plugin cancels refreshes, waits up to shutdownTimeout, then detaches export and removes its meters. A JDBC call that ignores interruption can outlive that bound; it can no longer publish to the exported registry. Database/driver query and network timeouts remain the installation’s responsibility. Failed startup also cleans up plugin-owned resources.

    Container exports include an engine tag to distinguish named engines. Existing single-engine Boot label sets remain unchanged. Scraping reads the last in-memory snapshot and does not issue new database queries. Script Guard’s total gauge is now refreshed on the snapshot cadence as well.

    History Level Requirements

    The extension’s counters are driven by the process engine’s history events, so they only fire for event types your configured eximeebpms.bpm.history-level actually produces. Most snapshot gauges read runtime state and are unaffected by the history level; finished-instance and ad-hoc database metrics have the requirements stated below.

    MetersMinimum history-level
    eximeebpms.process.instances.started, .endedactivity
    eximeebpms.process.instances.finished.totalactivity
    eximeebpms.tasks.created, .completed, .deletedactivity
    eximeebpms.external.tasks.started, .endedfull
    eximeebpms.incidents.created, .resolved, .deletedfull
    All gauges (*.running.total, *.open.total, *.open.age.*, jobs.failed.total, etc.)none — read runtime tables directly
    eximeebpms.script.violations, .totalnone — driven directly by the script-execution engine's own violation callback, not a history event or a runtime-table read
    eximeebpms.business.events.outbox.pending.estimate, .pending.age.oldest.secondsnone — read the Business Events outbox table directly
    eximeebpms.business.events.publish, .dispatch.batch.database, .dispatched, .dispatch.last.activity.age.secondsnone — driven directly by the business-event dispatcher's own callback

    Important

    At history-level: activity or audit, incident and external-task lifecycle counters silently stay at zero — the engine simply never produces those history events at those levels, so no error is raised. The Spring Boot starter defaults eximeebpms.bpm.history-level to full, so this only matters if it has been explicitly lowered.

    Business Events Outbox

    Enterprise Edition 1.4.3-ee and later

    These gauges are included in the co-released Enterprise monitoring modules since 1.4.3-ee. Earlier engines require a compatible standalone monitor release and the BusinessEventService#getOutboxBacklog() API; do not assume an older pinned extension contains them.
    MeterTypeDescription
    eximeebpms.business.events.outbox.pending.estimateGaugeUpper bound on the business events written to the outbox but not yet delivered to the configured publisher: the width of the outbox id range from the oldest undelivered event to the newest event. Not a count — see below.
    eximeebpms.business.events.outbox.pending.age.oldest.secondsGaugeHow long the oldest undelivered business event has been waiting. It stays close to the dispatch interval while delivery works. It grows steadily when the dispatcher is held on an event, because the receiver is unreachable or keeps rejecting it — see When Publishing Fails.

    Both gauges are registered only while Business Events are enabled, and carry no tags.

    Both gauges are read from the two ends of the outbox’s id index — the oldest undelivered id, the newest id, and the creation date of the oldest — and never by counting rows. The cost of a snapshot therefore does not grow with the backlog, which is also why the extension reports no exact count: counting would scan every pending event on every snapshot, on every node, just when the database is already behind. Measured on PostgreSQL with 5 million pending events, the count took about 220 ms with its index fully in memory, and the backlog read about 0.1 ms. On PostgreSQL, finding the oldest undelivered id also steps over the index entries of events delivered since the table was last vacuumed. That part of the read follows the dispatcher’s progress since the last vacuum, not the backlog: 3 ms with 250,000 such entries in the same measurement. Autovacuum keeps it small.

    pending.estimate is exact only while outbox ids have no gaps, and in practice they do. Every transaction that wrote business events and then rolled back, such as an optimistic-locking retry, consumes ids without leaving rows. Oracle and IBM DB2 identities discard up to 20 cached ids on restart, and SQL Server up to 1,000. On Oracle RAC, each instance hands out ids from its own cache, so ids are not in creation order across instances. Read the gauge as a trend: steady while delivery keeps up, growing when it falls behind. For an alert threshold, prefer pending.age.oldest.seconds, which has no such bias.

    Both values come from BusinessEventService#getOutboxBacklog(), which any deployment can call, including Tomcat and WildFly. An exact count is available on demand from createBusinessEventOutboxQuery().unprocessed().count(), at a cost that grows with the backlog.

    Business Events Dispatcher

    Enterprise Edition 1.4.3-ee and later

    These meters are included in the co-released Enterprise monitoring modules since 1.4.3-ee. Earlier engines require a compatible standalone monitor release and the BusinessEventDispatchListener API; do not assume an older pinned extension contains them.

    The dispatcher reports every publish attempt and every batch, so these meters keep moving during a long drain rather than only when a cycle ends. Every pass of the dispatcher reads at least one batch, so each pass leaves a sample, even when there is nothing to publish.

    MeterTypeDescription
    eximeebpms.business.events.publishTimerTime spent in the publisher per business event, tagged result (success, failure). A slow or unreachable receiver shows here: with the REST publisher, a timeout appears as a failure sample of about the request timeout.
    eximeebpms.business.events.dispatch.batch.databaseTimerTime a batch spends outside the publisher — reading it, marking it delivered and committing — tagged outcome: dispatched, empty, failed, lock-contended (another node holds the rows), error (the batch was rolled back and will be published again), interrupted.
    eximeebpms.business.events.dispatchedCounterBusiness events published and marked delivered on this node.
    eximeebpms.business.events.dispatch.last.activity.age.secondsGaugeSeconds since this node's dispatcher last completed a batch. A batch that was rolled back (error) does not count. It stays below the dispatch interval plus one batch while the dispatcher runs; alert when it grows.

    These meters are registered only while Business Events are enabled. Percentile histograms are off by default; enable one per meter with Spring Boot’s management.metrics.distribution.percentiles-histogram.<meter-name>=true.

    Script Guard

    MeterTypeDescription
    eximeebpms.script.violationsCounterIncremented on every Script Guard rule violation, tagged with the offending script's context (see Tags).
    eximeebpms.script.violations.totalGaugeLatest total from the configured Script Guard store, refreshed on the snapshot cadence and independent of tag values. Its lifetime follows that store and its retention; it is not a process-local counter.

    Ad-hoc subprocesses

    MeterTypeMeaning
    eximeebpms.adhoc.turns.decisions.totalGaugeSum of database-reported decision turns (COMPLETED or BPMN_ERROR) plus this node’s unreported count
    eximeebpms.adhoc.turns.tasks.replaced.totalGaugeSum of turn tasks replaced by another turn
    eximeebpms.adhoc.activations.totalGaugeSum of inner flows started by activations of any source
    eximeebpms.adhoc.model.callsCounterWorker-reported model calls on completed turns
    eximeebpms.adhoc.model.tokens.inputCounterWorker-reported input tokens on completed turns
    eximeebpms.adhoc.model.tokens.outputCounterWorker-reported output tokens on completed turns

    The first three gauges exist only if the engine counts these database metrics (metricsEnabled and the ad-hoc meters registered). They work at every history level. They include persisted counts from all nodes plus the local unreported count; another node’s count appears after its database reporting interval (15 minutes by default). Deleting database metrics can lower the gauge. These are gauges, despite .total in their names: do not apply counter-reset assumptions to them.

    The last three counters require history level audit or full, count only COMPLETED turns, and ignore usage fields the worker did not report. Tags are tenant.id, process.definition.id, process.definition.key, activity.id (the ad-hoc subprocess). Boot additionally requires history eventing; the container uses its direct history handler. They reset with the node, like the existing event counters.

    Configuration

    The extension provides the following Spring Boot properties. enabled controls all automatically configured engine listeners, periodic state measurements and worker monitoring, including the explicit @EnableMonitoring path. It leaves the engine, the host Micrometer registry and the separately secured Prometheus endpoint intact. Restart the application after changing these startup settings.

    When migrating from the separate monitor, eximeebpms.monitoring.snapshot.enabled and eximeebpms.monitoring.snapshot.updateRate keep their meaning. The new eximeebpms.monitoring.enabled has broader scope: false disables event-driven and worker meters as well as polling. Explicitly supplied application observers/meters remain application-owned.

    PropertyDefaultDescription
    eximeebpms.monitoring.enabledtrueEnable all automatic EximeeBPMS engine and worker measurements. Run explicitly sets this to false in default.yml and true in production.yml.
    eximeebpms.monitoring.snapshot.enabledtrueEnable the periodic state refreshes (gauges) only; event counters and worker meters are unaffected. See Cluster Considerations.
    eximeebpms.monitoring.snapshot.updateRate10000Delay, in milliseconds, between completed periodic state refreshes; event counters update when their events occur.

    Cluster Considerations

    Enable monitoring on every instance whose local event counters are required. Each enabled engine instance also refreshes the database-state gauges. These gauges describe the same shared database, so select one instance’s series or aggregate equivalent series without summing them (for example, use max while preserving the process-definition labels). Counter rates from different instances can be summed because they count local events. To reduce polling, set eximeebpms.monitoring.snapshot.enabled=false on all but one node (in containers, the plugin’s snapshotEnabled=false); their event counters keep running. Do not disable the global switch for this: it would also remove their event counters.

    Reporting Limitations

    The extension’s counters do not look up EximeeBPMS’s history database, which keeps it lightweight and scalable. When an instance restarts or crashes, its counters reset to zero — so counter values in the monitoring system may not be exact. This is acceptable for application monitoring but not for reporting use cases that require exact figures. For exact reporting, use the history database directly or a history event handler — see History Configuration.
